# 合成後の映像・音声の中身を E2E テストで大雑把に検証できるようにする

- Priority: Low
- Created: 2026-05-29
- Completed:
- Model: Opus 4.7
- Branch: feature/add-e2e-media-content-checks
- Polished: 2026-05-29

## 目的

現状の E2E テスト (`tests/e2e.rs`, `testdata/e2e/*`) は、合成後の MP4 ファイルに対してサンプル数・解像度・コーデック・トラック長といった **構造的** な検証は行っているが、合成された映像・音声の **内容** に対する検証は限定的。シングルソースのケースで「画面が赤一色か (YUV 値域チェック)」「無音期間がないか」を見ているのみで、複数ソースを合成した結果が「期待通りの領域配置になっているか」「期待通りの音が含まれているか」までは確認していない。

ピクセル単位の厳密な期待値一致は、エンコーダー (libvpx, openh264, svt-av1, VideoToolbox, NVENC) の世代差・ハードウェア差・量子化の揺れにより現実的に困難。一方、**大雑把な性質の検証** であれば実現の余地が多い (領域ごとの平均色、シーン切替点の位置、音声の RMS や周波数帯の有無、無音区間の検出 等)。本 issue では、何を「大雑把な検証」として E2E に組み込めるかを **検討から始める**。

## 優先度根拠

- 現状でも構造的チェックは行われているため、明らかな不具合 (合成が空になる、サンプル数が極端に少ない等) は検知できている。緊急度は低い。
- 一方、レイアウト変更の回帰や、scaler / mixer / encoder のパラメーター変更による出力品質低下は、現状の構造チェックでは見逃される。中身検証があれば早期検知できる価値は明確。
- 「ピクセル単位は無理」が前提なので、実装の難所は「検証手法の選定」と「許容誤差の設計」に偏る。検討せず実装に入ると過剰チェックや flaky test を量産する恐れがある。Low で検討先行が妥当。

## 現状

### 既存 E2E テスト

- `tests/e2e.rs:1474` 行
  - `simple_single_source_*` 系: 単一ソースで合成 → 出力 MP4 を inspect / decode してチェック。
  - サンプル数 (`audio_stats.total_sample_count == 51`, `video_stats.total_sample_count == 25`)
  - 解像度 (`resolutions == [(320, 240)]`)
  - トラック長 (`total_track_duration == 1s`)
  - コーデック (`expected_video_codec`, `expected_audio_codec`)
  - エンジン (`expected_video_engine`)
- 中身検証の現状 (`tests/e2e.rs:293-322`):
  - **音声**: 各 Opus サンプルをデコードして「全 0 でない」ことを確認 (= 完全な無音でないことを保証)。
  - **映像**: 各フレームをデコードして YUV 各 plane の値域をチェック (`y in 80..=83`, `u in 90..=91`, `v in 240..=241`)。これは入力が「赤色 320x240」の前提に基づく値域。
- マルチソース系 (`simple_multi_sources`, `multi_sources_single_column`, `two_regions` 等) のフィクスチャはあるが、中身検証は構造的チェックのみで内容検証はしていない (要再確認、現時点の grep ベースでは内容検証コードが見つからない)。

### 検証パスのインフラ

- `decode_video_frames_with_pipeline()` (`tests/e2e.rs:327-`) で、収集した encoded video sample を `MediaPipeline` 上で復号して `VideoFrame` 列を取り出すヘルパーが既にある。マルチソース合成の出力にも適用可能な構造。
- 音声は `OpusDecoder` を直接使って復号 (Opus 限定)。AAC については現状の中身検証はない (= 中身まで見るには AAC デコードルートも整備が必要)。

### testdata の組み立て方

- 各 fixture (`testdata/e2e/<name>/`) に `layout.jsonc` と入力ソース (例: `red-noise.mp4`) が同梱されている。
- 入力ソースは「赤一色 + ノイズ音」のような **特性が明示的に分かるパターン** を使っている。これは内容検証に有利な土壌になっている。

### Python 側 (`e2e-tests/obsws/`)

- obsws API のテストが中心で、メディア中身の検証は行っていない (`e2e-tests/recordings/` に録画 mp4 が並んでいるが、固定 fixture としての利用)。
- Python 側は OS / 依存関係が増えるため、メディア解析を Python (numpy / pillow / scipy) に寄せる選択肢もあるが、Rust 側でも十分書ける。

## 設計方針 (検討内容)

検討の論点を列挙し、現時点の見立てを残す。本 issue は検討完了をもって close、結論ごとに実装 issue を切り出す。

### Q1. 「大雑把」をどこまで認めるか

検証手法の候補:

| 手法 | 何を確かめるか | 実装コスト | flaky リスク |
| ---- | -------------- | ---------- | ------------ |
| (V1) YUV plane 値域 (既存) | 単色・近似色 | 低 | 低 (値域 4〜5 で吸収可) |
| (V2) 領域別平均色 | 「左半分が赤、右半分が青」のような領域配置 | 中 | 中 (枠の境界部分が混色する) |
| (V3) ヒストグラム比較 | 主要色が含まれているか | 中 | 中 |
| (V4) フレーム間差分 | 動きや切替点の有無 | 低〜中 | 低 |
| (V5) perceptual hash (pHash 等) | 参照画像と概ね一致するか | 中 | エンコーダーで揺れる |
| (V6) PSNR / SSIM | 参照画像との品質指標 | 高 (実装に外部 crate 要) | 高 (閾値の決定が難しい) |
| (A1) 振幅・RMS | 無音/有音の判定 | 低 | 低 |
| (A2) ゼロクロス検出 | 周波数帯の概要 | 低 | 中 |
| (A3) FFT バンドエネルギー | 特定周波数の有無 | 中 | 中 |
| (A4) 無音区間の長さ | 期待された無音時間が出ているか | 低 | 低 |

**推奨**: 第一弾は (V1), (V2), (V4) と (A1), (A4) に絞る。PSNR/SSIM/pHash は「やる前から flaky になりそう」なので保留。

### Q2. 期待値の表現方法

選択肢:

- (a) **テストコードにハードコード**: 現状の `matches!(x, 80..=83)` の延長。fixture ごとに領域配置と期待色をコード内に書く。
- (b) **fixture ディレクトリに JSON で期待値**: `testdata/e2e/<name>/expected_content.json` のような形で、領域ごとの期待色や RMS 閾値を持つ。
- (c) **参照画像/参照音声を fixture に置く**: バイナリ比較 (大きすぎるため非推奨)。

**推奨**: (b)。同じレイアウト fixture で複数の検証 (構造 + 内容) を組み合わせやすく、新規 fixture 追加時も決まった JSON だけ書けばよい。

JSON スキーマ案:

```json
{
  "video": {
    "regions": [
      {"name": "left",  "x": 0,   "y": 0, "w": 160, "h": 240,
       "avg_yuv":   {"y": [70,100], "u": [80,100], "v": [220,255]},
       "tolerance": "default"},
      {"name": "right", "x": 160, "y": 0, "w": 160, "h": 240,
       "avg_yuv":   {"y": [40,80],  "u": [110,140], "v": [60,100]},
       "tolerance": "default"}
    ],
    "frame_diff": {"min_change_ratio": 0.0, "max_change_ratio": 0.05}
  },
  "audio": {
    "rms":         {"min": 0.05, "max": 0.5},
    "max_silence": "0.1s"
  }
}
```

### Q3. 許容誤差 (tolerance) の設計

- YUV の平均色は **領域 (region) ごとに範囲指定**。`[low, high]` の閉区間で書く。
- 領域境界のピクセル混色を吸収するため、評価時に **領域から数ピクセル inset した中央部分** だけを集計する (例: 領域の上下左右 5px をスキップ)。
- エンコーダーごとに圧縮量子化の差が出る部分は、`tolerance` プロファイル (`default` / `loose` / `strict`) を用意して fixture ごとに選べるようにする。

### Q4. ハードウェア / 環境依存

- VideoToolbox は macOS, NVENC は GPU 付き CI 専用、SVT-AV1 は CPU 重い、など環境差が大きい。
- 既存の `simple_single_source_vp9_nvcodec` のように **環境ごとに fixture / テストを分ける** 既存ルールを継承する。内容検証も同様に環境別に書く。
- 共通の内容検証ロジック (region 平均色集計、RMS 計算等) はプラットフォーム非依存に切り出す。

### Q5. 実装場所と再利用性

- 共通の検証ヘルパー (`tests/common/media_content.rs` 等) を作り、`tests/e2e.rs` から呼び出す。
- ヘルパーは pure Rust。シンプルなアルゴリズムで `tests` 配下に置く (他テスト crate からも使えるように `tests/common/mod.rs` 形式が望ましい)。
- 既存の `decode_video_frames_with_pipeline()` を再利用してフレームを取り出し、ヘルパーに渡す形にする。
- 音声側も同様に「encoded 音声 → デコード → サンプル列」のヘルパーを 1 つ作り、Opus / AAC / Linear PCM の各経路に対応する。

### Q6. 失敗時の診断容易性

- 内容検証は flaky になりがちなため、失敗時に **何が違ったか分かるダンプ** を必ず出す。
  - 領域平均色チェック失敗 → 失敗領域名 + 期待範囲 + 実測値。
  - フレーム差分異常 → 失敗フレーム番号 + 算出値。
  - RMS 異常 → 期待範囲 + 実測値 + 該当時刻範囲。
- 必要なら失敗時に **デコード済みフレームを PNG で吐く** オプションを `--features dump-failed-frames` で用意する。CI で artifacts として収集できれば原因究明が楽。

### Q7. 実行時間

- 既存の `simple_single_source_*` は 1 秒の動画で完結している。内容検証を入れても合計実行時間は数秒のオーダーに収まる見込み。
- マルチソース系で 1 秒以上の fixture を増やす場合は、内容検証が走るとデコード負荷で実行時間が増える。基準として「1 fixture あたりの実行時間 3 秒以内」程度の目安を設けて、超えたら短い動画で代替する。

## 解決方法

### 検討手順

1. 既存の `simple_multi_sources` / `two_regions` の fixture を 1 つ選び、現状の合成結果を一度実際に確認する (`cargo run -- compose ...` → 出力を player で確認 or ffprobe / 自前デコードで YUV ダンプ)。
2. 上記出力に対して、Q1 の手法 (V1)(V2)(V4) を Rust 側のテストヘルパーで実装し、期待値を JSON で記述してみる pilot を作る。
3. pilot を libvpx / openh264 / SVT-AV1 / VideoToolbox / NVENC の各エンコーダーで動かして、許容誤差がどの程度必要かを実測する。
4. 結果を踏まえ、Q2 のスキーマ、Q3 の tolerance、Q5 の実装場所を確定する。
5. 音声側 (Opus + AAC) も同様に (A1)(A4) で pilot し、AAC のデコード経路を E2E ヘルパーで整備する必要があるかを判断する。
6. 結論をまとめて本 issue に追記、close。

### 留意事項

- 「中身検証が flaky で CI を不安定にした」前例を残してしまうと長期的に検証の信頼が落ちる。最初の導入では **少数の fixture に限定** し、安定運用が確認できてから拡大する。
- 領域配置 (V2) の検証は、入力ソース側に **領域ごとに明らかに違う色** を仕込む fixture を新規に増やすのが現実的。既存の `red-noise.mp4` のような単色入力では領域分割を「検証可能」にしづらいので、`blue-tone.mp4` のような別色入力も追加する想定。
- AAC デコードは外部依存 (audio_toolbox / fdk_aac) に左右され、E2E の実行環境制約を増やす。AAC の中身検証は当面はオプション扱いとし、Opus を主軸にするのが軽い。
- ハードウェアエンコーダー (VideoToolbox / NVENC) の出力は再現性が低い場合がある (バージョン差で量子化が変わる)。これらの環境では内容検証を **`#[cfg]` で部分的に緩める** か、構造的チェックのみに留める運用が必要かもしれない。
