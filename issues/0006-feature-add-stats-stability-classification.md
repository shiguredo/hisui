# 統計項目の安定・不安定の分類を導入できないかを検討する

- Priority: Low
- Created: 2026-05-29
- Completed:
- Model: Opus 4.7
- Branch: feature/add-stats-stability-classification
- Polished: 2026-05-29

## 目的

hisui は Prometheus 形式で多数の統計項目 (`hisui_*` メトリクス) を `/metrics` で公開している。現状、これらの項目はすべて区別なく公開されており、利用者から見ると **どの項目が長期的に互換性が保たれるか / どの項目は予告なく名前や型が変わりうるか** が判別できない。利用者がダッシュボードやアラート定義をどこまで安全に組めるかを判断できるようにするため、各項目に「安定 / 不安定 (experimental)」の分類を導入し、不安定な項目には `unstable="1"` のようなラベルを付与するなどして利用者に伝えられるようにしたい。

ただし、ラベル設計・分類基準・既存項目の振り分け・ドキュメント形式など未定の論点が多いため、本 issue は **検討から始める** ものとし、結論を踏まえて実装は別 issue として切り出す。

## 優先度根拠

- 緊急度は高くない。現状でも /metrics は機能しており、不安定項目が原因でユーザーに迷惑がかかった事例は把握していない。
- 一方、長期的には公開メトリクスの後方互換 (= 「安定と宣言した項目は壊さない」) のコミットメントを定義しておかないと、軽微な変更でも外部のダッシュボードが壊れる事故につながる。早めに方針だけでも整えておく価値はある。
- 実装より「何を安定とするか」の合意形成のほうがコストが高いタイプで、Medium にすると実装の手戻りが大きそう。まず Low で検討する位置付けが妥当。

## 現状

### 統計の仕組み

- `src/stats.rs:11` (`Stats`)
  - 6 種類のメトリクス型: `Counter`, `Gauge`, `GaugeF64`, `Duration`, `StringValue`, `Flag`。
  - キーは `metric_name: &'static str` + `default_labels: Arc<StatsLabels>`。
  - `set_default_label(name, value)` で個別の `Stats` インスタンスごとにラベルを追加。
- 既に使われているデフォルトラベル例:
  - `processor_id`, `processor_type` (`src/media_pipeline.rs:661-662`)
  - `component` (`src/rtsp/subscriber.rs:103,116` の `audio_decoder` / `video_decoder`)
  - `engine`, `codec` (encoder/decoder 内で `string("engine")`, `string("codec")` で動的セット)
- メトリクス生成呼び出し: 約 200 箇所 (`grep` で `.counter("`, `.gauge("`, `.gauge_f64("`, `.duration("`, `.string("`, `.flag("` を数えて 202 件)。一意の名前 (`metric_name`) はこれより少なく、コーデックごとに同名のメトリクスが多重生成されている (counter `total_audio_data_count` など)。

### 公開経路

- `src/endpoint_http_metrics.rs`
  - `GET /metrics` で Prometheus text format を返す。
  - `?format=json` で Prometheus JSON family 形式も返す。
  - `to_prometheus_text()` で `hisui_<metric_name>` プレフィックス付きで出力 (`stats.rs:8` の `PROMETHEUS_METRIC_PREFIX`)。
- 加えて tokio ランタイムメトリクス (`tokio_num_workers` 等) を `endpoint_http_metrics.rs:103-119` で合成。これらは hisui の `Stats` 経由ではなく直接 `StatsEntry` を生成して付加。

### 項目の分類（現時点で見えている観察）

明文化された分類はない。観察上、項目は概ね次のカテゴリに分かれている (要再確認):

- **長期保証したい**: 録画合成成功/失敗カウンタ、エンコーダー総処理フレーム数、エラーフラグなど、外部監視で頻繁に使われそうなもの。
- **内部状態に近い**: パイプラインの内部キュー長、デバッグ用のフレーム単位タイムスタンプなど。
- **デバッグ目的**: `processor_type` ごとのきわめて細かい内訳。
- **tokio ランタイム由来**: `tokio_*` プレフィックス。tokio のバージョンアップで増減しうる。

## 設計方針 (検討内容)

検討すべき論点を列挙し、各々で現時点の見立てを残す。本 issue は検討完了で close とし、結論ごとに実装 issue を切り出す。

### Q1. 「不安定」を表現する手段

選択肢:

| 案 | 内容 | メリット | デメリット |
| -- | ---- | -------- | ---------- |
| (A) Prometheus ラベル | `hisui_foo{unstable="1"} 42` | 既存のラベル機構に乗せられる、利用者が `{unstable!="1"}` でフィルタ可 | ラベル選択肢が無限大の場合に series 数が増える懸念。今回は 1/0 の二値なので影響は限定的 |
| (B) メトリクス名で区別 | 不安定なものは `hisui_unstable_foo` のように prefix | 名前を見るだけで分かる | 安定化したときにリネーム不可（互換維持のため新旧両方を並走させる必要） |
| (C) 別エンドポイント | 安定 `/metrics`、不安定 `/metrics/unstable` | クリアな分離 | プログラム側の実装コストが大きい、利用者が両方を意識する必要 |
| (D) HELP コメントで明示 | `# HELP hisui_foo (unstable) ...` | Prometheus 標準形式に近い | プログラム可読ではない、scrape 側でフィルタしにくい |

**推奨は (A)**。Stats のラベル機構と相性がよく、`unstable="1"` の有無で `relabel_config` や PromQL でのフィルタが容易。安定化する際は単に値を出さなくなるだけで済む。

二値表現の具体形は `unstable="1"` か `stability="experimental"` か議論余地あり:

- `unstable="1"`: 単純、`!=` フィルタが直感的。
- `stability="stable"` / `stability="experimental"` / `stability="deprecated"`: 将来的に 3 状態を表現したくなったときに拡張しやすい。

「将来 deprecated を表現したい可能性は十分あり」なので `stability="..."` を本命候補とし、結論として記録する。

### Q2. 分類基準

安定 / 不安定の判断はメトリクスごとに人手で行う必要がある。判断軸の素案:

1. **外部監視で典型的に使われそうか**: 録画失敗、エラーフラグ、エンコーダーのスループットなどは安定寄り。
2. **内部実装に強く依存していないか**: 内部キュー長や processor 数といった「リファクタで意味が変わるもの」は不安定寄り。
3. **依存ライブラリ由来か**: `tokio_*` は tokio のバージョンに従属するため不安定。
4. **コーデック実装の詳細を露出していないか**: コーデック単位の細かい統計は不安定寄り（コーデック追加・削除で増減する）。
5. **メトリクス型変更の余地があるか**: Counter から Gauge への変更を検討中など、型が揺れる可能性のあるものは不安定。

第一弾は **「明らかに安定」と確信できるもの以外を不安定 (`stability="experimental"`) とする** 保守的な分類にする。安定リストは小さく始めて、運用ログを見ながら拡張する。

### Q3. プログラム側の実装

- `Stats::counter(name)` 等の API はそのまま残し、**安定化したいメトリクスだけホワイトリスト** をどこかに集約する。
  - 例: `src/stats_stability.rs` に `const STABLE_METRICS: &[&str] = &[...]` を置き、`to_prometheus_text` 出力時にこのリストに含まれない名前へ `stability="experimental"` を自動付与する。
  - メリット: メトリクス生成側のコードを変更しない (約 200 箇所を触らなくて済む)。
- 反対案: 各 `counter("foo")` 呼び出しに `stable()` などの fluent API を追加して明示する。
  - メリット: 生成箇所で分類が明示される。
  - デメリット: 200 箇所の修正が必要、忘れたら不安定扱いになる (今回はそれで OK だが、明示する文化が要る)。

**第一候補**: ホワイトリスト方式。Rust 側のコード変更は 1 ファイルで済み、分類の見直しもファイルを編集するだけで完結する。

### Q4. ドキュメント化

- 安定リスト = ドキュメントに記載する項目、というシンプルな整理にする。
- 形式:
  - `docs/metrics.md` を新規作成し、各安定メトリクスについて 1 行で「名前 / 型 / ラベル / 意味」を記載。
  - 不安定項目は **意図的にドキュメント化しない**。
- 不安定の宣言は「ドキュメントに載っていない = 不安定」 + 「ラベルでも識別可能」の二重で利用者に伝える。

### Q5. 安定項目の変更プロセス

「安定」とした項目を後で変えたくなる場合のプロセスを決めておく必要がある:

- 安定 → 非互換変更: 旧名を残しつつ新名を追加 → 旧名に `stability="deprecated"` を付ける移行期間 → CHANGES.md `[CHANGE]` で告知 → 翌マイナーで旧名削除。
- 安定 → 廃止: 同様に `stability="deprecated"` を経由して告知してから削除。
- 不安定 → 安定: ドキュメントに追記、ラベル `stability` 削除、CHANGES.md `[ADD]` または `[UPDATE]`。

この運用は Q1 で `stability="..."` を採用した場合に自然に表現できる。

### Q6. tokio runtime メトリクスの扱い

- `tokio_num_workers`, `tokio_num_alive_tasks`, `tokio_global_queue_depth` は **常に不安定** 扱い (tokio のバージョン依存)。
- これらは `hisui_` プレフィックスもついていないため、プレフィックスで自然に区別されている (`endpoint_http_metrics.rs:103-119`)。
- 整理として、tokio_ 系には `stability="experimental"` を付ける、もしくは「`hisui_` 以外のメトリクスは全部 unstable」と明文化する案がある。後者の方が運用しやすい。

## 解決方法

### 検討手順

1. 既存メトリクスを棚卸しする。手元で `cargo run -- server --port 0 --emit-startup-info` 相当を起動 (issue 0002 の機能を仮想して、現状なら手で port を指定) し、しばらく動かしてから `curl http://127.0.0.1:<port>/metrics` で取得して一覧化する。
   - 一覧化スクリプトは `scripts/list-metrics.sh` 程度の薄いシェルで OK。
2. 一覧を見ながら、Q2 の基準で安定 / 不安定を仮分類する。第一弾は「明らかな安定」のみ抽出し、残りは不安定扱い。
3. Q1 のラベル方式が問題ないか、Prometheus / Grafana 側の relabel / PromQL 動作を簡易に試す (`stability="experimental"` フィルタで series が消えること)。
4. Q3 の実装方式 (ホワイトリスト vs fluent API) を、サンプル実装を書いて比較する。実装着手前の比較なので、PoC は本 issue とは別ブランチで一時的に書いて捨てる。
5. Q4 のドキュメント形式 (Markdown 表 + コードリンク) を 1 メトリクスでサンプル化し、運用負荷を確認する。
6. 上記を踏まえて結論をまとめ、本 issue の末尾に追記して close する。

### 留意事項

- 検討段階なのでコード変更は最小限。PoC は別ブランチに留め、main / develop には混ぜない。
- メトリクスの安定宣言は **後で剥がしにくい** ため、第一弾はかなり保守的に絞る。「外部監視で典型的に使われそう」だけで判断せず、「コードリファクタで壊れる可能性が極小」も条件にする。
